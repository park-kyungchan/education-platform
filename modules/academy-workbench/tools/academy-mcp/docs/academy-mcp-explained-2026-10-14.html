검사 프로그램이 실제 Academy MCP process를 실행했습니다. process는 실행 중인 프로그램입니다. 검사 프로그램은 MCP 도구를 발견하고, 정해진 형식으로 호출하고, 응답을 읽었습니다.

학생 명단 5명을 여러 페이지로 읽었습니다. 첫 번째 학생에 대해서는 요약, 9종 기록, 날짜별 수업 맥락을 호출했습니다.

SCOPE NOT ESTABLISHED

전체 담당 학생이라는 목표는 유지

대상은 박경찬 담당 학생 전체입니다. 현재 원본 파일에는 5명이 보존되어 있습니다. 전체 담당 학생 수는 확인되지 않아 응답에서 null로 표시합니다. null은 값이 확인되지 않았다는 표시입니다.

실시간 학원 조회, 전체 학습 이력, native Codex 등록은 검증되지 않았습니다.

학원서버에 대한 read-only 경계를 지켰습니다. read-only는 자료를 읽고 원본을 바꾸지 않는다는 뜻입니다. 이번 Academy MCP에는 학원 네트워크 요청을 보내는 코드가 없습니다. DailyRecord 입력, 저장, 학부모 전송, 출력물 생성, 채점, 초기화 기능도 노출하지 않습니다.

Git은 파일 상태와 변경 이력을 관리하는 프로그램입니다. repository는 Git으로 관리하는 프로젝트 파일 집합입니다. clone은 그 파일과 이력을 로컬에 복제하는 동작입니다. 확인 시 PR #12는 이미 병합되어 있었습니다. PR은 변경 내용을 검토하고 병합하기 위한 GitHub 기록입니다. 그 변경이 반영된 main을 clone했습니다.

기준 commit은 900616a09b54742418ca333cd30e391e8cfc069b입니다. commit은 특정 시점의 파일 상태를 기록한 Git 데이터입니다. 새 구현은 clone 내부의 tools/academy-mcp/에 있습니다. 이 새 디렉터리는 현재 로컬의 미커밋 작업입니다. 공통 Harness 적용과 저장소 통합은 보류했습니다. Harness는 공통 실행·맥락·검증 규칙을 제공하는 구성입니다.

02

파일, 코드, 실행 중인 프로그램을 구분하기

파일이 있다고 해서 그 파일이 스스로 실행되지는 않습니다. Bun이 TypeScript 코드를 읽어 실행하면 process가 생깁니다. 그 process가 파일을 읽고 입력을 검사하고 응답을 만듭니다.

용어이번 작업에서의 뜻
TypeScript / .ts허용할 값의 형식을 함께 작성하는 프로그래밍 언어와 그 코드 파일입니다. 실행 전에 형식 오류를 검사할 수 있습니다.
Bun이 프로젝트의 TypeScript 파일을 실행하고 필요한 소프트웨어 묶음을 설치하는 프로그램입니다.
JSON / .json이름과 값을 묶어 저장하는 텍스트 형식입니다. 원본 자료, 계약, 검증 결과를 이 형식으로 기록했습니다.
schema이름, 값의 종류, 필수 항목, 허용 범위를 정한 규칙입니다. Zod라는 라이브러리가 실제 입력을 이 규칙과 비교합니다. 라이브러리는 다른 코드가 가져다 쓰는 기능 묶음입니다.
client / serverclient는 도구 호출을 요청하는 프로그램입니다. server는 요청을 받아 처리하는 프로그램입니다. 이번 server는 로컬 process이며 인터넷에 공개한 서버가 아닙니다.
stdioprocess의 표준 입력과 표준 출력을 사용하는 통신 방식입니다. client가 자식 process를 실행하고 두 프로그램 사이에서 요청·응답을 주고받습니다.
dependency / lockfiledependency는 실행이나 개발에 필요한 소프트웨어입니다. lockfile은 설치할 정확한 버전과 연결 정보를 고정한 파일입니다. 이 프로젝트는 bun.lock을 사용합니다.

새 구현의 파일 구조

tools/academy-mcp/
├── src/             실행 코드와 타입
├── architecture/    작업 의도와 원본 고정값
├── schemas/         코드에서 생성한 계약
├── tests/           검사 코드와 가상 자료
├── verification/    실제 검증 결과
├── docs/            이 설명 문서
├── package.json     의존성과 실행 명령
├── bun.lock         설치 버전 고정
├── mcp.launch.json  실행 방법을 적은 파일
└── handoff.json     완료 범위와 인계 정보

파일을 용도별로 묶은 구조입니다. 위에서 아래로 실행된다는 뜻은 아닙니다.

파일별 책임

  • src/server.tsMCP 도구 3개를 등록하고 stdio 통신을 시작합니다.
  • src/service.ts시작 검사를 수행하고 각 도구 호출을 처리합니다.
  • src/contracts.ts학생 조회 입력·출력의 타입과 실제 검사 규칙을 정의합니다.
  • src/saved-context.ts보존 자료를 읽고, 정확한 학생과 기록을 선택합니다.
  • src/catalog.ts · src/taxonomy.ts원천 기능의 선언과 업무 분류를 제공합니다.
  • src/pagination.ts페이지 크기와 다음 페이지 위치를 검사합니다.

MCP 프로그램의 실행 코드는 이 파일들을 가져다 사용합니다. mcp.launch.json은 실행 정보일 뿐입니다. 파일을 만든 것만으로 native Codex에 도구가 등록되지는 않습니다.

연결 관계는 별도 설계입니다

topology는 항목 사이에 어떤 연결이 있는지 나타내는 구조입니다. WORKFLOW_RELATIONS는 업무 사이의 의미 관계를 별도로 기록합니다. 예를 들어 수업과 과제 사이에는 날짜와 학생 범위를 확인해야 한다는 관계가 있습니다.

이 관계의 상태는 design_relation_requires_source_join_evidence입니다. 두 원본의 기록을 연결하려면 별도의 근거가 필요하다는 뜻입니다. 이 설계 기록이 자동으로 학생 자료를 합치거나 다음 업무를 실행하지는 않습니다.

95개는 실행 가능한 API 수가 아닙니다. API는 프로그램이 요청할 수 있도록 정한 기능과 입력·출력 규칙입니다. 여기의 95개는 기존 자료에 적힌 원천 기능 설명입니다. 모두 runtimeCallable:false, execution:not_available로 유지했습니다.

원천 선언에는 read 30개, write 19개, unknown 44개, 발송 화면 열기 1개, 발송 1개가 있습니다. read는 읽기, write는 변경, unknown은 효과를 확인하지 못한 분류입니다. GET은 HTTP 요청 방식의 이름입니다. GET으로 선언된 기능 중에도 자료를 바꾸는 기능 11개가 있어 excluded_write로 분류했습니다. 요청 방식만 보고 읽기 기능으로 판단하지 않았습니다.

04

프로그램은 원본 검사부터 시작합니다

다음은 server.ts를 실행할 때의 순서입니다. 이 문서는 순서를 설명할 뿐, 해당 명령을 실행하지 않습니다. 오른쪽 도식은 스크롤 위치에 따라 현재 설명하는 부분을 표시합니다.

START 01 · LOCAL PROCESS

Bun이 코드를 실행하고 두 읽기를 시작합니다

server.ts의 첫 준비 작업은 loadService(repoRoot)입니다. 이 함수는 필요한 자료를 준비해 AcademyService를 만드는 코드입니다.

함수는 loadCatalog()와 loadSavedContext()를 Promise.all()로 함께 시작합니다. Promise는 아직 끝나지 않은 작업의 결과를 나타내는 값입니다. 두 작업이 모두 성공하면 Promise.all에서 두 결과를 함께 받습니다. 하나라도 실패하면 초기화가 실패합니다.

한 작업은 기능 목록을 읽습니다. 다른 작업은 보존 학생 자료와 수업 보충 자료를 읽습니다. 두 작업의 시작 순서를 학생 자료 다음 기능 목록처럼 고정하지 않았습니다.

다음 단계의 조건: 두 읽기가 모두 성공해야 합니다. 하나라도 실패하면 초기화가 실패하며 도구 통신을 시작하지 않습니다.
START 02 · SOURCE CHECKS

정해진 파일인지, 고정한 내용과 같은지 비교합니다

loadSavedContext()는 허용된 원본 경로 두 개만 읽습니다. 하나는 학생 audit 파일, 하나는 수업 overlay 파일입니다. audit는 보존한 조사 기록이며, overlay는 별도로 준비한 수업 보충 기록입니다. 호출자가 URL이나 임의 경로를 지정할 수 없습니다.

lstat()으로 파일 정보를 읽습니다. 일반 파일인지 확인하고, 다른 경로를 가리키는 symlink 파일을 거부합니다. 각 보존 원본의 크기는 32 MiB 이하여야 합니다. MiB는 파일 크기 단위이며 1 MiB는 1,048,576 bytes입니다.

SHA-256은 파일의 byte 내용에서 계산하는 고정 길이 값입니다. pin은 사용하기로 고정한 원본의 경로와 SHA-256 기록입니다. 프로그램은 읽은 byte의 SHA-256을 계산해 source-pins.json의 값과 비교합니다.

그다음 JSON을 읽고 자료 형식을 검사합니다. 수업 보충 자료의 학생 ID도 audit에 있는 ID와 맞아야 합니다. 준비된 원본 객체에는 Object.freeze()를 적용합니다. 이 함수는 해당 객체의 내용을 실행 중 바꾸지 못하게 합니다.

통과: 경로·파일 조건·해시·형식이 모두 맞습니다. 실패: 어느 하나라도 맞지 않으면 시작을 중단합니다. 해시 일치는 고정한 파일과 byte가 같다는 뜻입니다. 학원서버의 최신 상태나 원본 내용의 사실성까지 증명하지는 않습니다.
START 03 · JOIN & SERVICE

두 결과가 준비되면 나머지 규칙을 검사합니다

loadService()는 두 결과를 받은 뒤 기능 목록의 해시가 pin과 같은지 확인합니다. 이어 intent.json의 파일 조건과 schema 버전을 확인합니다. 이 파일에는 합의한 작업 목적과 원천 제약이 있습니다.

business-decisions.json은 보존된 업무 규칙입니다. 프로그램은 파일 조건과 해시를 검사합니다. 또 authorityGranted:false인지, decisions가 배열인지 검사합니다. 배열은 여러 값을 순서대로 담은 형식입니다.

모든 검사를 통과하면 AcademyService 객체를 만듭니다. 이 객체는 기능 목록과 보존 자료를 받아 도구 호출을 처리합니다. 보존된 업무 규칙은 실행 권한을 부여하지 않습니다.

실패 후 처리: 자동 재시도는 없습니다. 원본 변경이 의도된 것인지 검토하고 필요한 pin을 갱신한 다음 새 process를 시작해야 합니다.
START 04 · REGISTRATION

준비된 service로 도구를 등록합니다

server.ts는 준비된 service를 받은 뒤 McpServer 객체를 만듭니다. MCP SDK는 MCP 통신 규칙을 구현한 라이브러리입니다. SDK는 software development kit의 약자입니다.

registerTool()을 세 번 호출해 이름, 설명, 입력 규칙, 실행 함수를 등록합니다. 세 도구 모두 읽기 전용이라는 annotation을 가집니다. annotation은 도구의 성질을 알리는 설명 값입니다. 실제 읽기 전용 동작은 코드와 검증으로 별도 확인했습니다.

마지막으로 StdioServerTransport를 연결합니다. transport는 두 프로그램 사이에서 메시지를 전달하는 구성입니다. 이때부터 client가 표준 입력으로 보낸 MCP 요청을 받을 수 있습니다. HTTP 포트는 열지 않습니다.

실행 중 자료: 이 process는 시작 때 읽은 하나의 변경 불가능한 snapshot을 계속 사용합니다. snapshot은 그 시점에 고정한 자료 상태입니다. 파일을 나중에 바꿔도 자동으로 새 자료를 읽지 않습니다.
05

학생 기록 한 번을 조회하는 순서

이번에는 시작이 끝난 process에 client가 academy_query를 호출하는 경우입니다. 파일 구조와 달리 아래 화살표는 한 요청을 처리하는 순서를 나타냅니다.

QUERY 01 · INPUT

client가 조회 종류와 학생 ID를 보냅니다

먼저 roster 조회로 보존 학생 목록을 읽습니다. 이후 학생별 조회에는 그 목록이 반환한 studentId 값을 그대로 사용합니다. 이 ID는 보존 자료 안의 정확한 식별 값입니다. 학생 이름이나 학원서버의 실제 ID를 대신 넣지 않습니다.

query.kind는 조회 종류입니다. roster, student_summary, student_records, lesson_context 중 하나만 허용합니다. kind에 따라 필요한 입력 항목도 달라집니다.

sourceMode는 자료를 읽는 방식을 나타냅니다. 이 프로그램은 saved_context만 허용합니다. 생략하면 같은 값이 기본값으로 적용됩니다.

QUERY 02 · CONTRACT CHECK

실제 값이 계약과 맞는지 검사합니다

contracts.ts의 Zod schema가 입력을 검사합니다. limit은 1부터 25까지의 정수여야 합니다. 정수는 소수 부분이 없는 수입니다. 생략하면 10을 사용합니다.

student_records에는 학생 ID와 facet이 필요합니다. facet은 조회할 기록 종류입니다. 허용된 9종 중 하나를 골라야 합니다. lesson_context에는 학생 ID와 유효한 YYYY-MM-DD 날짜가 필요합니다.

입력 객체는 strict() 규칙을 사용합니다. 허용하지 않은 이름의 항목을 추가하면 실패합니다. URL 입력, live 모드, 잘못된 값의 종류는 이 검사에서 거부합니다.

실패 결과: 입력 형식이 틀리면 MCP 오류 응답이 됩니다. 정상적인 조회 결과에 빈 기록을 넣어 성공처럼 처리하지 않습니다.
QUERY 03 · EXACT SELECTION

SavedContext가 해당 학생의 원본 행을 선택합니다

AcademyService.query()가 SavedContext.query()를 호출합니다. SavedContext는 시작 때 고정한 보존 자료와 조회 코드를 가진 객체입니다. 학생 ID가 보존 명단에 정확히 있는지 확인합니다.

명단 밖 ID면 다른 학생이나 예시 자료를 반환하지 않습니다. student_not_in_preserved_roster라는 code와 status:"unavailable"을 반환합니다. unavailable은 그 조회를 제공할 수 없다는 뜻입니다.

학생이 확인되면 선택한 facet의 원본 행을 읽습니다. 행은 보존된 기록 항목 하나입니다. 교재 판본 필터는 books와 sections에만 적용합니다. 판본은 특정 교재 버전입니다. 해당 학생의 books 원본에 있는 sourceBookEditionId 값을 조회 입력의 bookEditionId에 넣습니다. sections도 같은 판본 ID로 선택합니다.

날짜별 수업 맥락은 정확한 학생 ID와 날짜를 비교해 보충 기록을 선택합니다. 보충 자료는 2명에 관한 별도 자료입니다. 전체 5명에게 같은 보충 내용을 적용하지 않습니다.

QUERY 04 · PAGINATION

선택한 기록을 정해진 크기로 나눕니다

pagination은 여러 기록을 여러 응답으로 나눠 읽는 방식입니다. 첫 응답에는 최대 limit개를 담습니다. 뒤에 기록이 남아 있으면 nextCursor를 돌려줍니다. cursor는 다음에 읽을 위치를 표현한 문자열입니다.

cursor 안에는 snapshot 해시, 검사된 query의 해시, 다음 offset이 있습니다. offset은 선택한 기록에서 다음에 읽을 위치를 나타내는 수입니다. 프로그램은 cursor의 형식과 길이를 확인하고, 두 해시가 이번 요청과 같은지 비교합니다. 위치가 선택한 행 수를 넘지도 않아야 합니다.

다음 요청은 같은 query와 받은 cursor를 함께 보냅니다. 다른 학생, 다른 필터, 다른 snapshot의 cursor면 거부합니다. cursor는 조회 위치 정보이며 권한을 증명하는 값이 아닙니다.

범위: exhausted:true는 현재 선택한 보존 행을 끝까지 읽었다는 뜻입니다. 학생의 전체 학습 이력을 확보했다는 뜻은 아닙니다. 기능 목록 도구는 이 cursor 대신 별도의 offset과 최대 50개 limit을 사용합니다.
QUERY 05 · OUTPUT

출처와 한계를 붙여 응답합니다

프로그램은 각 응답 행에 분류, 값, 파일 경로, 파일 해시, JSON pointer를 붙입니다. JSON pointer는 원본 JSON 내부 위치를 표현한 문자열입니다. 일반 기록 조회는 원본 값을 보존하고 그 행의 위치를 가리킵니다. roster는 원본 학생 항목에서 일부 필드를 선택합니다. summary는 그 학생의 보존 행 수를 계산합니다. 이 두 결과의 pointer는 반환 필드 전체가 아닌 근거가 된 원본 학생 항목을 가리킵니다.

retrievedAt에는 로컬 프로그램이 응답을 만든 시간을 넣습니다. 원본 수집 시각인 collectedAt, 수업 날짜인 lessonDate, 보충 기록 준비 시각인 lessonPreparedAt은 따로 유지합니다.

AcademyService는 결과를 출력 schema와 비교합니다. 통과한 결과를 server.ts가 JSON 텍스트와 structuredContent로 함께 반환합니다. structuredContent는 client가 항목별로 읽을 수 있는 구조화된 응답 값입니다. 출력 계약에 맞지 않으면 MCP 오류로 끝나며 정상 결과를 반환하지 않습니다.

보존 범위만 읽은 정상 결과는 status:"partial"입니다. partial은 전체 원천을 다 확인한 결과가 아니라는 표시입니다. 응답이 직렬화 후 512 KiB를 넘으면 제공 불가 결과를 반환합니다. 직렬화는 객체를 전송 가능한 JSON 텍스트로 바꾸는 동작입니다.

항상 유지하는 표시: currentAcademyServerQueried:false, absenceProvesNonperformance:false. 이번 응답은 원서버 최신 조회가 아니며, 기록 부재로 학생 미수행을 판정하지 않습니다.
06

작은 입력 예시로 계약 읽기

아래 JSON은 설명용 예시입니다. 실제 학생 이름이나 ID, 기록 값은 포함하지 않았습니다. 이 문서에서 입력을 전송하지 않습니다.

VALID INPUT SHAPE · ROSTER

보존 학생 목록 2개 요청

{
  "sourceMode": "saved_context",
  "query": { "kind": "roster" },
  "limit": 2
}

query.kind가 roster라서 학생 ID를 받지 않습니다. limit이 2이므로 한 응답에 최대 두 행을 반환합니다. 나머지가 있으면 다음 cursor가 생깁니다.

SYNTHETIC VALUE · NOT A REAL STUDENT

{
  "sourceMode": "saved_context",
  "query": {
    "kind": "student_records",
    "studentId": "EXAMPLE_ONLY_STUDENT_ID",
    "facet": "assignments"
  },
  "limit": 10
}

위 학생 ID는 가상 값입니다. 형식 검사를 통과해도 보존 명단에 없는 값이므로 실제 호출에서는 unavailable이 됩니다. roster가 반환한 ID를 그대로 써야 자료를 읽을 수 있습니다.

실패 조건과 실제 결과

입력 또는 상태프로그램의 판단다음 행동
sourceMode:"live", URL 추가, limit:26, 잘못된 날짜입력 schema 실패 → MCP 오류허용된 kind와 값 범위로 입력을 고칩니다.
형식은 맞지만 명단에 없는 학생 IDunavailable · student_not_in_preserved_rosterroster에서 정확한 ID를 확인합니다. 다른 학생으로 대체하지 않습니다.
다른 query나 snapshot의 cursorunavailable · cursor_scope_or_snapshot_conflict원하는 query를 cursor 없이 처음부터 요청합니다.

선택한 보존 행이 0개partial · 빈 records · 범위 한계 표시추가 원본이 필요한지 검토합니다. 미수행이나 삭제로 해석하지 않습니다.

unavailable 결과의 records는 빈 배열입니다. totalInSavedSelection은 null입니다. returned는 0, exhausted는 false, nextCursor는 null입니다. 오류로 제공하지 못한 결과를 “확인한 자료가 0개”로 오해하지 않도록 구분했습니다.

academy_capabilities의 조회 방식도 구분됩니다. view:"hierarchy"는 업무 계층, operations는 기능 목록, source_contract는 정확한 operation ID의 선언, workflow_rules는 보존 업무 규칙입니다. operation은 원천 기능 항목 하나입니다. 조회한 선언을 실행하는 기능은 없습니다.

07

자료가 있다는 것과 업무가 끝났다는 것은 별개입니다

기록의 분류와 시간을 보존한 이유는 실제로 확인한 사실의 범위를 유지하기 위해서입니다. 요약을 계산해도 원본의 불확실성이 없어지지는 않습니다.

분류 값뜻이 값만으로 확인할 수 없는 것
saved_source_record원천에서 보존한 기록현재 원서버에도 같은 값이 있는지
teacher_report교사가 보고한 내용서버가 독립적으로 확인한 수행 완료
user_supplied_context사용자가 제공한 맥락관찰되지 않은 원천 기록
source_observation_snapshot특정 시점에 관찰해 보존한 내용그 뒤의 변경 또는 과거 전체 이력
unsaved_draft사이트에 저장되지 않은 초안DailyRecord 저장이나 학부모 발송 완료
derived_saved_summary보존 자료에서 계산한 요약고유 과제 수, 학습 완료, 교사 검토 완료

시간은 네 가지를 구분합니다

collectedAt은 원본 수집 시각입니다. lessonDate는 수업 날짜입니다. lessonPreparedAt은 수업 보충 자료를 준비한 시각입니다. retrievedAt은 로컬 조회 응답을 만든 시각입니다.

retrievedAt이 새 시각이어도 원본이 새로 수집된 것은 아닙니다. 현재 process는 같은 snapshot을 읽습니다.

출처를 행마다 돌려줍니다

source.path는 원본 파일 경로입니다. source.sha256은 그 파일 내용의 고정값입니다. source.jsonPointer는 근거가 있는 파일 내부 위치입니다. 일반 기록의 value는 원본 값을 유지합니다. roster는 필드를 선택하고 summary는 값을 계산하므로 해당 결과는 원본 학생 항목을 근거로 표시합니다.

필터를 적용해도 원본 행 위치를 보존합니다. 학생 이름이 비슷하다는 이유로 다른 파일을 연결하지 않습니다. 원본 필드를 서로 다른 의미의 값으로 바꾸지 않습니다.

사이트의 “2주 비노출”을 삭제로 처리하지 않습니다

“2주가 지나면 사이트에서 학생 자료를 숨긴다”, “서버에 자료는 남지만 권한 때문에 직접 조회할 수 없다”는 사용자에게 보고받은 제약입니다. 독립적으로 검증한 API 보존 기간 계약은 아닙니다.

이번 코드는 보존 자료에 2주 age filter를 걸지 않습니다. age filter는 날짜가 오래됐다는 이유로 기록을 제외하는 조건입니다. 이미 보존한 기록은 사이트에서 보이지 않게 되었다는 이유로 제외하지 않습니다.

반대로 파일에 없는 오래된 기록을 복원한 것은 아닙니다. 누락된 자료가 필요하면 권한이 허용하는 새 원본 확보 방법을 별도로 검토해야 합니다.

입력: 보존 기록을 찾지 못함

프로그램이 확인한 것은 “현재 고정한 파일과 선택 조건에서 반환할 행이 없다”는 사실입니다.

응답: 범위를 표시한 빈 결과

미수행·삭제·발송 실패로 판정하지 않습니다. unknowns 항목에 남은 불확실성을 표시합니다. unknowns는 확인되지 않은 내용을 적는 목록입니다.

08

REA 설치와 최적화에서 확인한 것

REA는 프로그램 파일을 분석하는 도구 모음입니다. reverse engineering은 기존 프로그램의 코드나 실행 자료에서 구조와 동작을 조사하는 작업입니다. 이번에는 REA를 clone 안에 설치하고 별도 MCP 연결과 정적 분석을 검증했습니다.

REA 6.5.0 · CATALOG MEASUREMENT

도구 이름은 같고, 목록 응답은 작아졌습니다

full과 compact 설정에서 도구 이름 207개가 같았습니다. 설정을 바꾸면서 도구 목록을 JSON 텍스트로 만든 byte 크기를 비교했습니다.

설정직렬화한 목록 크기
full3,087,952 bytes
compact214,813 bytes
감소율약 93.04%

감소율 = (full − compact) ÷ full × 100. 같은 이름 확인과 목록 크기 측정입니다. 207개 기능 각각의 동작이 같다는 전체 검증은 아닙니다.

STATIC ANALYSIS · PARTIAL COVERAGE

분석 대상은 합성 프런트엔드 파일입니다

preview/v21/app.js는 프로젝트에 포함된 합성 예시 프로그램입니다. 프런트엔드는 사용자 화면 쪽 프로그램입니다. REA는 이 파일을 실행하지 않고 읽어 정적으로 분석했습니다.

분석 결과에는 application graph와 semantic graph가 있습니다. graph는 항목과 연결을 표현하는 자료 구조입니다. 분석 범위는 partial로 기록했습니다. 실제 학원 백엔드 전체나 API의 동일 동작을 확인한 결과가 아닙니다.

분석 증거는 clone 내부 .local/rea-api/에 보존했습니다. Academy MCP의 읽기 도구에서 REA 분석 실행이나 결과 파일 쓰기를 호출하지 않습니다.

측정의 한계: 93.04%는 직렬화한 목록의 byte 감소율입니다. 모델이 읽는 token 수나 안정적인 응답 지연 감소율을 측정하지 않았습니다. token은 모델이 텍스트를 처리할 때 사용하는 단위입니다.

설치 범위: 이번 JavaScript 분석과 MCP 검증에 필요한 dependency를 프로젝트 내부에 설치했습니다. native decompiler나 instrumentation 전체를 설치·검증했다고 주장하지 않습니다. decompiler는 실행 파일에서 읽을 수 있는 코드를 재구성하는 도구입니다. instrumentation은 실행 중인 프로그램을 관찰하기 위해 코드를 삽입하거나 연결하는 방식입니다.

고정한 주요 dependency: MCP client/server 2.3.1, REA 6.5.0, Zod 4.4.3, TypeScript 7.0.2, bun-types 1.4.2. 검증 환경 기록: Bun 1.3.14, Node.js 22.22.1. bun-types는 Bun 기능의 타입 정의입니다. Node.js는 REA의 JavaScript 실행에 사용한 프로그램입니다.

세션 이력의 구분: 초기 DailyRecord 작업에는 browser 로그인과 공식 메뉴 읽기가 있었습니다. 사용자가 그 작업을 취소하고 범위를 바꾼 뒤 현재 구현을 진행했습니다. “학원 요청 0”은 이번 보존 자료 MCP의 구현·검증 범위입니다. 전체 대화에서 사이트를 한 번도 열지 않았다는 뜻은 아닙니다.

남은 작업과 설명의 근거

이 단계에서는 읽을 수 있는 자료의 범위를 정확히 드러내는 조회 계약을 완성했습니다. 전체 학생 확보와 업무별 연결은 별도의 자료·권한·검증이 필요한 후속 작업입니다.

  1. 전체 담당 명단 확인: 권한이 허용하는 원본을 확보하고 현재 5명과 비교해야 합니다. 목표 범위와 보존 범위가 같다는 근거가 필요합니다.
  2. 보존 자료 추가: 새 파일의 내용·분류·식별 관계를 검토하고 pin을 갱신해야 합니다. 새 process에서 새 snapshot을 읽어 검증해야 합니다.
  3. 업무별 adapter 구현: adapter는 원천의 자료 형식과 업무 조회 계약을 연결하는 코드입니다. 기존 95개 선언 중 실제 read-only 동작과 권한을 확인한 기능부터 순차 구현해야 합니다. mutating GET은 읽기 기능으로 연결하지 않습니다.
  4. native 등록과 사용 검증: 현재 launch descriptor를 바탕으로 별도 범위에서 연결해야 합니다. descriptor는 실행 방법을 적은 자료입니다. 이후 실제 도구 발견과 호출을 확인해야 합니다.
  5. 공통 Harness 적용: 사용자가 보류한 저장소 간 통합·분리와 공통 규칙 적용은 후속 범위입니다.
