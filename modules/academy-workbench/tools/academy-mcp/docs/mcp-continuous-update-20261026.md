# MCP tools 지속 업데이트 원칙 (2026-10-26)

학원 사이트·앱 표면은 수시로 바뀌고, MCP 도구는 그 표면을 read-only로 따라간다.
이 문서는 변경 감지부터 도구 갱신·실증까지의 반복 절차와 남은 RE 항목의 우선순위를 정한다.
쓰기·발송·출력·결제 성격은 소유자 승인 없이 열지 않는다. 자격증명 값은 어떤 단계에서도 출력·기록하지 않는다.

## 반복 절차

1. 사이트 변경 감지: 네이티브 런처의 핀 검증(`native_launch_pin_drift`,
   페이지 스크립트 digest 불일치, wire-drift)이 1차 신호다. 핀 불일치는
   추측·우회 대상이 아니라 계약 재확인 트리거다.
2. 계약 재확인: 정적 증거(핀된 번들 JS 텍스트, REA 분석 기록, 저장된 관측)로
   와이어 계약을 다시 고정한다. 바이너리가 아닌 JS 텍스트에는 Ghidra를 쓰지 않는다.
   새 서블릿·새 파라미터가 필요하면 소유자 확인을 named blocker로 남긴다.
3. 도구 갱신: workbench에 계약을 구현하고 fixture 테스트를 추가한다.
   백엔드 미주입 상태는 `*_backend_not_configured`로 fail-closed 하며,
   실패는 요청 단위로 닫는다(세션 latch 금지).
4. 신규 세션 실증: 교체된 설치본을 새 브리지 프로세스로 띄워
   tools/list, source_status, roster, 해당 읽기 경로를 확인한다.
   기존 세션에 로드된 구 프로세스 결과는 증거로 쓰지 않는다.
5. 등록 단일화: 모든 런타임이 같은 중립 설치본을 가리키는지 확인한다.
   런타임별 복사본은 핀·버전 drift의 원인이므로 두지 않는다.

## 남은 RE 항목 (우선순위순)

- P1 이름 검색 소유자 번들 노출: workbench 포트 + 승인 테이블 폴백 +
  fixture는 완료. 남은 소유자 단계는 (a) 네이티브 DailyRecord 번들을
  workbench 소스로 재빌드, (b) 런처 핀(바이트·sha) 재발행, (c) 브리지
  재발견으로 `academy_student_resolve`를 dailyrecord 엔드포인트에 매핑,
  (d) 신규 세션 실증. 그전까지 브리지 resolve는 fail-closed를 유지한다.
- P2 미노출 읽기군 대조: teacher_query/report, item-label 3종, cism_section,
  pool 6종은 workbench에 구현돼 있으나 중립 브리지에 미노출이다.
  노출은 브리지 엔드포인트 추가 + 레지스트리 재발견 + 설치본 verify 갱신으로
  가능하며, 백엔드 미주입 상태에서는 fail-closed로만 뜬다.
  노출 범위 결정과 백엔드 주입은 소유자 승인 후 별도 PR로 한다.
- P3 95개 인벤토리 잔여: 저장된 95개 연산 카탈로그와 노출 19개 도구의 차분은
  인벤토리 문서에 둔다. 와이어 증거 없는 신규 연산은 구현하지 않는다.

## 금지선

- 숫자 ID 추측·순차 대입 금지. 이름→키 확인은 정확 일치 1행만 인정한다.
- 실패한 요청의 자동 재시도 금지. 다음 요청은 새 판정을 받는다.
- 이 문서·테스트·receipt에 자격증명·원본 학생 데이터를 넣지 않는다.
